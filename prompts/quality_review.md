# 단위테스트 문안 품질 검토

아래 초안은 JSON 구조 검증을 통과했다. 동일한 소스 근거와 출력 JSON 계약을 유지하면서 테스트 가치와 문장 품질을 한 번 더 검토한다.

검토 순서

1. 개발 의뢰의 핵심 변경 주제와 변경된 분기 조건을 초안이 실제로 다루는지 확인한다.
2. 정상 흐름만 반복했다면 선택된 diff와 소스에 조건과 처리 결과가 함께 확인되는 변경 없음, 오류, 경계, 권한, 삭제 영향, 이름변경 호환성, 회귀 후보만 반영한다. 일반적인 가능성이나 넓은 의뢰 문구만으로 실패 시나리오를 만들지 않는다.
3. scenarios가 한 개 이상 다섯 개 이하이고 success가 한 개 이상인지 확인한다. 기본 목표는 서로 다른 검증 의도 약 세 개지만 근거가 부족하면 한두 개를 유지한다.
4. 사전조건에서 클래스, 객체, 메서드, 쿼리, 파일의 구현 존재 여부를 제거하고 테스트 실행 전에 준비할 수 있는 상태로 바꾼다.
5. 근거에 없는 한국어 업무 사실, 역할, 계정, 외부 시스템, 상태값, 화면, API, 데이터값을 만들지 않는다.
6. 오탈자, 번역투, 모호한 정상 동작 표현을 없애고 사람이 작성한 짧고 자연스러운 한국어로 다듬는다.
7. 단순 변경을 억지로 여러 시나리오로 부풀리지 않고 큰 변경도 파일 목록이 아니라 핵심 사용자 흐름과 위험을 최대 다섯 개의 독립 시나리오로 통합한다.
8. 각 scenario 안의 procedure에는 저장, 조회조건 지정, 다운로드, 삭제, 권한 거부, 오류 입력 등 근거가 있는 실제 조작을 쓰고 expectedResult에는 그 조작과 직접 대응하는 사용자의 관찰 결과를 쓴다. 서로 다른 scenario의 절차와 결과를 교차 결합하지 않는다.
9. 각 scenario의 testData에 식별 가능한 값이 있다면 선택된 근거에 실제로 존재하는지 확인하고 한국어 조사와 쉼표로 자연스럽게 연결한다. 파생 계산값은 expectedResult에만 둔다.
10. 각 scenario의 expectedResult는 한 개 또는 서로 직접 연결된 두 개 결과만 남기되, 전체 scenario 수를 두 개로 제한하지 않는다.
11. scenarios 출력 JSON 계약과 evidenceRefs를 유지하고 JSON 객체 하나만 출력한다.
12. 로컬 품질 진단에서 근거 있는 사용자 조건이 누락되었다면 같은 scenario 안에 실제 조작과 관찰 결과를 추가한다. 반대로 선택된 소스 근거가 없는 validation, boundary, permission, error, regression은 억지로 보완하지 말고 제거하거나 실제 근거가 있는 종류로 교정한다.
13. testData가 기간별 입력 데이터나 설정처럼 값과 조건이 없는 이름이거나 클래스명과 컴포넌트명이라면, 근거에 있는 실제 필드 값과 빈 값 및 경계 조건으로 바꾼다. 근거가 없으면 빈 문자열로 두고 시나리오를 억지로 만들지 않는다.
14. procedure와 testData와 expectedResult에 px와 rem과 minmax 및 CSS 속성이 있으면 제거한다. 값 기반 업무 시나리오가 있으면 순수 스타일 시나리오는 제거하고 처리내역에만 남기며, 스타일만 변경된 경우에는 잘림과 겹침 및 정렬처럼 사용자 관찰 결과로 바꾼다.
15. testCase.notes는 모든 시나리오를 종합한 한 문장만 유지한다. 시나리오 유형과 제목을 대괄호로 반복하거나 시나리오별 비고를 만들지 않는다.
