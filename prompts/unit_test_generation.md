# 프롬프트 계약

# 목표

개발 의뢰와 변경 근거를 함께 분석해 하나의 통합 단위테스트 문안을 작성한다. 항목 수는 커밋과 파일 수가 아니라 독립적인 검증 의도로 결정한다. 기본 목표는 서로 다른 검증 의도를 가진 독립 시나리오 세 개이며 근거의 크기와 위험에 따라 한 개 이상 다섯 개 이하로 조정한다. 정상 케이스인 success는 반드시 한 개 이상 포함하고, validation과 boundary와 permission과 error와 regression은 실제 근거가 없으면 한 개도 만들지 않는다.

# 분석 순서

1. 문서 시스템명은 환경설정 값을 사용하고 개발 의뢰에서는 업무 배경을 찾되, 넓은 의뢰 범위 자체를 모두 이번 테스트 대상으로 간주하지 않는다.
2. 사용자 입력 변경 요약과 선택된 Git 커밋 및 diff를 이번 변경의 우선 근거로 사용하고, 변경 목록의 신규, 변경, 삭제와 실제로 바뀐 조건, 계산, 조회, 저장, 표시 동작을 찾는다.
3. 언어와 프레임워크에 맞는 정확한 import, include, 호출 대상, endpoint, 데이터 객체와 계약으로 연결된 소스를 사용해 입력에서 결과까지의 흐름을 교차 확인한다.
4. 변경을 업무 동작별로 묶고 각 묶음에서 진입점, 입력 조건, 실행, 호출 계층, 데이터 계약, 관찰 가능한 결과와 직접 근거를 내부적으로 정리한다.
5. 먼저 사용자가 직접 입력하거나 선택할 수 있는 업무 데이터의 대표 정상 흐름을 success 후보로 정하고, 변경된 검증 조건, 빈 값, 최솟값과 최댓값, 권한 거부, 명시적 오류 처리, 기존 계약 유지 중 선택된 diff와 소스와 fixture에서 실제로 확인되는 후보만 추가한다.
6. 한 시나리오는 입력 조건과 실행과 예상결과와 판정 기준이 모두 닫힌 하나의 검증 의도를 가진다. 화면 열기, 값 입력, 저장, 결과 확인처럼 같은 목적의 연속 단계를 여러 시나리오로 쪼개지 않는다.
7. 같은 동작의 화면과 서버 파일뿐 아니라 Python 모듈, SQL 객체, JSP include, SAP 프로그램과 CDS처럼 서로 연결된 구현은 별도 시나리오로 중복 계산하지 않고 실행 진입점에서 업무 및 데이터 결과까지 하나의 시나리오로 묶는다.
8. 서로 다른 저장과 조회와 삭제와 다운로드 동작이나 서로 다른 분기 조건처럼 입력과 기대 결과가 달라질 때만 별도 시나리오로 분리한다.
9. validation과 boundary와 permission과 error와 regression은 단순히 일반적으로 발생할 수 있다는 이유로 만들지 않는다. 실행 조건과 기대 결과가 선택된 변경 근거에서 모두 뒷받침되어야 한다.
10. 개발 의뢰의 권한, 메뉴, DB 같은 넓은 표현은 선택된 변경 파일이나 diff에서 직접 뒷받침될 때만 시나리오로 채택한다.
11. 각 시나리오의 근거를 evidenceRefs로 남기고, 각 참조는 선택된 입력 근거에 그대로 나타나는 파일 경로, 식별자, 상태값 또는 데이터 리터럴이어야 한다.
12. 각 문장이 근거에서 확인되는지 점검하고 확인되지 않는 고유명사, 역할, 업무 규칙, 식별자를 제거한다.
13. 시나리오 우선순위는 업무 입력값과 계산 및 저장 결과, 입력 검증과 오류 및 경계 분기, 권한과 호환성, 화면 이동과 상태 유지, 순수한 색상과 간격 및 폭 변경 순서다. 앞선 검증 후보가 있으면 순수 스타일 변경을 독립 시나리오로 승격하지 않는다.
14. 순수 스타일 변경만 있는 경우에도 px와 rem과 minmax와 CSS 속성 및 컴포넌트 설정명을 문안에 쓰지 않고, 잘림 없이 읽히는지와 정렬이 흐트러지지 않는지처럼 사용자가 눈으로 판정할 결과로 바꾼다.

# 필드 작성 기준

documentTitle

- 환경설정 시스템명은 `{{SYSTEM_NAME}}`이다. 값이 자동 감지이면 개발 의뢰에서 근거가 확인되는 시스템명을 작성하고, 화면명이나 업무명을 시스템명으로 추측하지 않는다.
- 확장자, 단위테스트, 날짜, 시간, 괄호를 제외한 시스템명만 사용한다.

testCase.name

- 핵심 변경 목적을 드러내고 단위테스트로 끝나는 한 문구를 작성한다.
- 접수번호는 개발 의뢰에서 정확히 확인된 경우에만 포함한다.

testCase.scenarios

- 기본 목표는 세 개이고 근거에 따라 한 개 이상 다섯 개 이하로 작성한다.
- success를 한 개 이상 포함한다. validation과 boundary와 permission과 error와 regression은 각각의 조건과 결과가 근거에 있을 때만 사용하며 개수가 0이어도 된다.
- 같은 사용자 흐름의 준비, 실행, 관찰 단계를 항목 수를 맞추기 위해 여러 객체로 나누지 않는다. 각 객체는 다른 입력 조건이나 다른 사용자 동작 또는 다른 위험을 검증해야 한다.
- 단순 변경에 독립 검증 의도가 하나뿐이면 한 개로 끝내고, 큰 변경도 파일별 목록이 아니라 핵심 동작과 위험을 다섯 개 안에 통합한다.
- 사용자 변경 요약의 각 줄을 반드시 한 시나리오씩 만들지 않는다. 값 입력과 오류 및 경계 분기가 확인되는 변경이 있으면 간격, 폭, 색상 같은 스타일 메모는 처리내역에만 남길 수 있다.

testCase.scenarios.kind

- 정상 사용 흐름은 success를 사용한다.
- 소스의 필수값, 허용값, 중복, 누락 검증은 validation을 사용한다.
- 소스에 명시된 최소, 최대, 0, 빈 값, 상한과 하한은 boundary를 사용한다.
- 실제 권한, 역할, 잠금, 접근 거부 분기는 permission을 사용한다.
- 실제 예외, 실패 응답, 재시도, 타임아웃, 오류 메시지 처리는 error를 사용한다.
- 변경 후에도 유지되어야 하는 기존 호출, 필드, 계산 또는 호환 계약은 regression을 사용한다.

testCase.scenarios.title

- 입력 조건과 검증 목적이 드러나는 짧은 명사형 문구로 작성한다.
- kind의 한국어 이름을 대괄호로 반복하거나 번호를 붙이지 않는다. kind와 title은 내부 품질 검토와 릴리즈 노트에만 사용하고 Excel에는 절차와 데이터와 결과가 번호로 표시된다.

testCase.scenarios.procedure

- 하나의 독립 시나리오를 실제로 실행할 수 있도록 입력 조건과 조작을 한 문장에 연결하고 다로 끝낸다.
- 저장은 입력값 또는 변경 상태를 만들고 저장을 실행하도록, 조회는 조회조건을 지정하고 조회하도록, 다운로드는 조건을 지정해 파일을 내려받도록 구체적으로 쓴다.
- 화면 열기, 값 입력, 저장, 결과 확인이 같은 검증 목적이면 한 시나리오 안에서 자연스럽게 연결한다.
- 변경 사항 확인, 기능 확인, 정상 동작 확인처럼 조작 대상과 조건이 없는 절차를 쓰지 않는다.

testCase.scenarios.testData

- 사용자 입력, 변경된 Git diff, 선택된 소스 또는 fixture와 mock에 실제로 나타난 값만 구체적인 코드값, 날짜, 금액, 비율로 작성한다.
- 근거에 구체적인 값이 없으면 임의 값을 만들지 말고 최신 기간 데이터, 변경 사항이 없는 입력처럼 근거에서 확인되는 조건으로 작성한다.
- fixture와 mock의 값은 테스트용 근거일 뿐 운영 데이터라고 표현하지 않는다.
- 계산식으로 얻는 비율과 합계와 상태는 입력 데이터가 아니므로 testData에 넣지 않고 expectedResult에 작성한다.
- 여러 값은 의미가 드러나도록 한국어 조사와 쉼표로 연결하고 별도 입력 데이터가 필요 없으면 빈 문자열을 사용한다.
- 테스트 담당자가 실제로 입력하거나 선택할 필드와 값 또는 의도적으로 비울 조건을 쓴다. 기간별 입력 데이터처럼 값과 조건이 없는 포괄적 명칭이나 Config 객체와 컴포넌트명 같은 구현 식별자는 테스트 데이터가 아니다.
- 같은 변경 분기에 정상값과 빈 값 및 경계값이 근거로 확인되면 각각의 testData에 대응 값을 나누어 작성한다. 절차를 testData에 다시 쓰지 않는다.

testCase.scenarios.expectedResult

- 해당 procedure와 testData로부터 사용자가 직접 관찰하거나 조회할 수 있는 결과를 한 문장으로 쓰고 다로 끝낸다.
- 파생값은 계산식과 입력값이 근거에서 확인될 때만 작성한다. 근거에 없는 숫자를 예상값으로 계산하거나 추측하지 않는다.
- validation과 boundary와 permission과 error는 기대한 차단, 제외, 오류 응답 또는 기존 값 유지가 나타나는 것을 성공 판정으로 쓴다.
- 정상 동작한다처럼 대상이 없는 표현만 사용하지 않는다.
- px와 rem 같은 화면 수치, CSS 속성, 클래스명과 컴포넌트 설정값은 예상결과에 쓰지 않는다. 순수 화면 변경을 검증해야 할 때는 잘림, 겹침, 정렬, 가독성처럼 사용자가 관찰할 결과만 쓴다.

testCase.notes

- 모든 scenario의 expectedResult를 종합해 이번 변경 범위가 정상이라고 판단할 수 있는 기준을 사용자 관점의 한 문장으로 쓰고 다로 끝낸다.
- 시나리오별 문장을 반복하거나 대괄호로 유형을 붙이지 않는다. 예상결과를 그대로 나열하지 않고 정상 입력과 오류 및 경계 처리 결과가 모두 예상과 같으면 해당 변경이 정상 반영된 것으로 판단한다는 정도로 통합한다.
- 빈 문자열과 줄바꿈을 사용하지 않는다.

testCase.scenarios.evidenceRefs

- 한 개 이상 여섯 개 이하로 작성한다.
- 선택된 입력 근거에 그대로 나타나는 변경 파일 경로, 메서드와 쿼리와 필드 식별자, 상태값 또는 테스트 데이터 리터럴만 사용한다.
- 시나리오의 입력 조건과 기대 결과를 실제로 뒷받침하는 참조를 우선하고 일반적인 단어만 넣지 않는다.
- 설명 문장, 근거 번호 추측, 존재하지 않는 행 번호를 만들지 않는다.

testCase.targetIds와 testCase.targetNames

- 화면, 배치 Step, 보고서 식별자와 이름이 근거에 그대로 있는 경우에만 작성한다.
- 클래스명과 파일명을 화면 이름으로 바꾸지 않는다. 불확실하면 빈 배열을 사용한다.

testCase.preconditions

- 실제 실행에 꼭 필요한 조건만 최대 다섯 개까지 작성하고 있어야 한다, 준비되어 있다처럼 다로 끝나는 자연스러운 완결 문장으로 쓴다.
- 모든 시나리오에 공통인 권한, 비교 기준 데이터, 실행 환경처럼 수행을 좌우하는 조건만 남기고 개별 입력 조건은 해당 시나리오에 작성한다.
- 권한, 기준 데이터, 실행 환경처럼 실제 절차에 필요한 조건을 쓰되 확인되지 않은 계정명과 데이터값을 만들지 않는다.
- 클래스, 객체, 메서드, 쿼리, 파일이 구현되거나 작성되어 있어야 한다는 식의 구현 존재 여부는 테스트 사전조건으로 쓰지 않는다.
- 별도 준비 조건이 없으면 빈 배열을 사용한다.

testResult.processingDetails

- 파일별 목록이 아니라 변경 주제별로 한 개 이상 다섯 개 이하를 작성한다.
- 단순 변경은 한 항목으로 충분하면 늘리지 않고 대규모 변경은 같은 업무 흐름의 수정 사항을 합쳐 다섯 항목 안에 정리한다.
- title은 변경 대상을 짧게 쓰고 detail은 무엇이 어떻게 바뀌었는지 한 줄로 쓴다.

testResult.resultChecks

- 핵심 판정 기준을 한 개 이상 다섯 개 이하로 작성한다.
- scenarios의 모든 expectedResult를 그대로 복사하지 않고 변경 전체에서 캡처하거나 최종 확인할 핵심 기준을 명사형 문구로 간결하게 쓴다.

# 품질 점검

JSON을 출력하기 전에 다음 조건을 모두 확인한다.

1. scenarios는 한 개 이상 다섯 개 이하이고 success가 한 개 이상 있다.
2. 각 scenario는 다른 검증 의도를 가지며 같은 흐름의 준비, 실행, 관찰을 여러 객체로 쪼개지 않았다.
3. validation과 boundary와 permission과 error와 regression은 조건과 결과가 선택된 diff와 소스와 fixture에서 확인될 때만 존재한다.
4. 각 scenario의 procedure와 testData와 expectedResult가 같은 입력 조건과 판정 의도로 연결되고 testCase.notes는 전체 결과를 한 문장으로 통합한다.
5. testData의 구체적인 값은 선택된 근거에 그대로 있으며 파생 계산값은 expectedResult에만 있다.
6. evidenceRefs의 모든 값은 선택된 입력 근거에서 그대로 검색되고 해당 시나리오를 실질적으로 뒷받침한다.
7. 고유명사와 식별자는 개발 의뢰 또는 소스 근거에서 확인된다.
8. 처리내역은 파일 수와 관계없이 업무 변경 주제로 묶였다.
